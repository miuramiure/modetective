# modetective v2 基本設計
作成：2026-11-25　入力：00_決定事項.md、v1一式（02.作業/20261105モデル探偵ゲーム）、ITB設計一式（02.作業/20261117イルミナティーブレイクオンライン設計）

## 1. 何をするアプリか
モデル探偵の**テーマの提示**だけを受け持つ進行アプリ。v1（静的ファイルのみ）と同じ画面の流れを、サーバーで同期させる。

| アプリがすること | アプリがしないこと（Balus・会議ツール側） |
|---|---|
| 部屋を作る（GM）、参加者がチームに入る | モデリング |
| カードを配る・引き直す・確定する（チーム全員で同じ画面） | タイマー |
| GMの操作でフェーズを進め、全員の画面を同時に切り替える | 回答・結論の記入、締め切りの管理 |
| フェーズごとに、見せてよいものだけを見せる（自分のカード、相手の目的の選択肢、場面リスト、解決編の公開） | 採点の入力・集計 |
| GMに各チームの状況（メンバー・確定したカード）と台本を見せる | ブレイクアウトルームの操作 |

**v1からの変化**
| v1 | v2 |
|---|---|
| ゲームURLに設定とカードを埋め込む | 部屋のURL（部屋コード）だけ。設定とカードはサーバーが持つ |
| 参加者が合言葉を入れて次のフェーズへ | **GMが進めると全員が切り替わる** |
| 事件番号を口頭で相手とGMに伝える | **なし**。サーバーが組み合わせを知っているので自動で見せる |
| 進み具合は各ブラウザが覚える | サーバーが覚える。チームのメンバー全員が同じ画面 |
| GMは各チームの状況が見えない | GM画面に一覧（誰がどのチームか、確定したか） |

## 2. 構成
```
 ブラウザ ──①画面──→ ConoHa WING  modetective.m-miura.jp   … index.html／JS／CSS（Viteのビルド結果）
    │
    └──②wss/https─→ GCP e2-micro itb-play（us-west1-b、ITBと同居）
                     games-api.m-miura.jp
                      Caddy :443
                       ├ /illuminatea/* → 127.0.0.1:3101  ITB
                       └ /modetective/* → 127.0.0.1:3102  modetectiveサーバー（Node.js、systemd）
                                            ├ Socket.IO（部屋・同期）
                                            ├ HTTP API（health）
                                            ├ ゲームの中心部（@mdt/core：カード読み込み・配布・フェーズ・見せ分け）
                                            ├ カードデータ（data/cards/<版>.md、v1と同じ書式）
                                            └ 部屋の保存（/var/lib/modetective/rooms.json）
```
- 新しいGCPリソースは作らない（VM・固定IP・ファイアウォールはITBのTerraform管理のまま）。VMの中に、ユーザー・ディレクトリ・systemdの単位・Caddyの振り分けを足すだけ。
- Caddyは、ITBのCaddyfileの games-api ブロックに `import /etc/caddy/games.d/*.caddy` を1行足し、各ゲームが自分の振り分けファイルを置く形にする（ITBとmodetectiveのリポジトリが互いのファイルを書き換えないため）。
- メモリ：e2-microは1GB（＋スワップ1GB）。modetectiveは小さいので MemoryMax=200M（ITBは600M）。

## 3. 用語
| 用語 | 意味 |
|---|---|
| 部屋 | 1回の遊びの単位。部屋コード（6文字）で表す。複数のセットを続けて遊べる |
| セット | テーマカードの提示〜振り返りの1周。部屋の中でセット番号が1,2,…と増える |
| チーム | G1-A、G1-B…。グループ番号＋A／B |
| メンバー | 参加者。ニックネームを持ち、どれか1つのチームに属する |
| GM | 部屋を作った人。GM合言葉を知っている人 |

## 4. 状態とフェーズ
### 4.1 部屋の状態（サーバーが持つ）
```
Room
  code            部屋コード（6文字。紛らわしい文字を除く）
  cardset         カードデータの版（部屋を作った時点で固定）
  settings        dist: common|individual（共通／個別カード）
                  mode: scenario|kikikomi（シナリオ／聞き込み）
                  purposeChoice: true|false（目的の選択肢あり／なし）
                  gmPlays: true|false（GMも参加）
                  groups: 1〜10
  setNo           セット番号
  phase           lobby | card | investigate | deduce | reveal | review
  decks           グループごとの A・B の山（引き直し候補を含むカードIDの列）。共通方式は全グループ共通の1組
  teams[G1-A…]    cardId（表示中のカード）、redrawsUsed、confirmed、confirmedBy（ニックネーム）
  members[]       tokenHash、nickname、team（未選択可）、connected
  gm              tokenHash
  log[]           GM画面に出す簡単な出来事（「G1-A：佐藤さんが引き直し」など、最新50件）
  createdAt, lastActiveAt
```
- カードの配り方・組み合わせ禁止の判定は v1（app.js の `deal`・`conflicts`・`poolFor`）と同じ考え方を移植する（v1設計メモ4章）。
- 引き直しの回数は2回（設定値）。共通カード方式では引き直しなし。

### 4.2 フェーズの進み方
| フェーズ | 画面名 | 参加者の画面 | 進め方 |
|---|---|---|---|
| lobby | 集合 | ニックネーム入力 → チーム選択 → 「GMの開始を待っています」 | GMが「カードを配る」 |
| card | カード提示 | 自分のチームのカード。引き直す／これでいく | GMが「調査フェーズへ」（未確定チームは自動確定＝K4） |
| investigate | 調査フェーズ | 確定カード、モデリングのルール、Balusの指示、（聞き込み）進め方 | GMが「推理フェーズへ」 |
| deduce | 推理フェーズ | 相手チームの目的の選択肢（選択肢ありの場合）、場面の選択肢リスト（モード分）、回答のひな形、自分のカード（折りたたみ） | GMが「解決編へ」 |
| reveal | 解決編 | 自分と相手のカードの場面・目的・判定メモを並べて公開、配点の早見表、判定の境界（該当場面の行） | GMが「振り返りへ」 |
| review | 振り返り | 全体共有の切り口、全グループのカード一覧（K7） | GMが「次のセット」→ card へ（K5） |
- GMは1つ前のフェーズに戻せる（押し間違い用）。戻しても確定したカードは変わらない。
- 途中から入ったメンバーは、チームを選ぶとそのフェーズの画面から始まる。
- チームの変更はいつでもできる（調査フェーズ以降は「チームを変えると、見えるカードが変わります」と確認を出す）。GMもメンバーをほかのチームへ移せる。

### 4.3 見せ分け（viewFor）
サーバーは、状態から**その人に見せてよいものだけ**を組み立てて送る。見せないものは通信に乗せない。

| 情報 | 自チーム | 相手チーム（同グループ） | 他グループ | GM（gmPlays=false） | GM（gmPlays=true） |
|---|---|---|---|---|---|
| 自チームのカード（全項目） | card〜 | reveal〜 | review〜 | 常に | reveal〜 |
| 目的の選択肢 | card〜 | deduce〜（選択肢ありのみ） | review〜 | 常に | deduce〜 |
| 場面の選択肢リスト | deduce〜 | ― | ― | 常に | 常に |
| 判定の境界（該当の行） | reveal〜 | reveal〜 | review〜 | 常に | reveal〜 |
| チームのメンバー名・確定の有無 | 常に | 常に | 常に | 常に | 常に |
- gmPlays=true のときのGMは、どのチームのカードも reveal までは場面・目的・お題を見ない（v1と同じ）。誤操作に備え「カードを見る（警告つき）」の折りたたみを置くかは実装で決めてよい。
- **テストで必ず確かめる**：あるフェーズの参加者向けの送信データ（JSON文字列）に、見せてはいけないカードの場面・目的・お題の文字列が入っていないこと。

## 5. 参加と認証
| 人 | 入り方 | 再接続 |
|---|---|---|
| GM | トップ画面でGM合言葉を入力 → 設定 → 部屋を作る | gmToken をブラウザに保存。別の端末では「部屋コード＋GM合言葉」で入り直せる |
| 参加者 | GMが配る部屋URL（`https://modetective.m-miura.jp/?r=部屋コード`）を開き、ニックネームを入れる | memberToken をブラウザに保存（部屋ごと）。閉じても同じチームに戻る |
- **GM合言葉**はサーバーの設定ファイル（/etc/modetective/env、root以外読めない）にハッシュで置く。1つの合言葉を全GMで共有（三浦さんが決めて、必要な人に伝える）。
- 合言葉の失敗は、IPごとに10分間5回まで（それ以上は一時的に拒否）。部屋の作成は1時間20回まで。
- 同じニックネームは同じ部屋で重ならないようにする（重なったら「佐藤(2)」）。
- トークンはサーバーではハッシュで持つ。トークンを他人に渡さない限り、なりすましはできない（紳士協定よりは強い程度で十分）。

## 6. 通信（Socket.IO）
- 接続先：`wss://games-api.m-miura.jp`、Socket.IOの path は `/modetective/socket.io`。Originは `https://modetective.m-miura.jp`（開発時は localhost も許可）だけ受け付ける。
- 操作はすべて ack 付き（`{ok:true,...}` か `{ok:false, code, message}`）。

| クライアント→サーバー | 送る人 | 内容 |
|---|---|---|
| `gm:create` | 誰でも | `{pass, settings}` → `{code, gmToken}` |
| `gm:login` | 誰でも | `{code, pass}` → `{gmToken}`（別の端末から） |
| `gm:resume` | GM | `{code, gmToken}` |
| `gm:updateSettings` | GM | lobby と review のときだけ |
| `gm:setPhase` | GM | `{to}`（次へ／1つ戻る） |
| `gm:nextSet` | GM | review から。カードを配り直して card へ |
| `gm:moveMember` | GM | `{memberId, team}` |
| `member:join` | 誰でも | `{code, nickname}` → `{memberToken}` |
| `member:resume` | 参加者 | `{code, memberToken}` |
| `member:chooseTeam` | 参加者 | `{team}` |
| `team:redraw` | 参加者 | `{setNo, cardId}`（いま見ているカード。古い画面からの二重押しを弾く） |
| `team:confirm` | 参加者 | `{setNo, cardId}` |

| サーバー→クライアント | 宛先 | 内容 |
|---|---|---|
| `view` | 各人に個別 | `viewFor(部屋, その人)` の結果＋`rev`（変更番号）。変化のたびに全体を送る（小さいので差分にしない） |
| `session:replaced` | 古い接続 | 同じトークンで別の接続が来た |
| `room:closed` | 全員 | 部屋の期限切れ |

HTTP：`GET /modetective/api/health` → `{ok, rooms, members, version}`（監視・デプロイ前の確認用）

## 7. カードデータ
- v1と同じ **共有用テーマカード集のmd** を正本にする（`data/cards/v0.4.md` のように版を付けて置く）。書式は v1 README のとおり。
- サーバー起動時に読み込んで検証する（カードの項目がそろっているか、場面が場面リストにあるか、目的の選択肢に正解が含まれるか、対応表の場面がリストにあるか）。おかしければ起動しない。
- テスト：v0.4 でシナリオ28枚・聞き込み20枚・場面リスト56／40個が読めること。v1の読み方（`parseCards`）を移植し、同じ結果になること。
- カード集を直したら：新しい版のmdを `data/cards/` に足し、既定の版を設定で切り替える。進行中の部屋は作ったときの版のまま。

## 8. 画面
v1の見た目（レヴィカラー：ティール #0097A7、差し色 黄 #FFBC1B、探偵の要素は控えめ）と文言・台本・Balusの指示枠をそのまま引き継ぐ。PCとスマホの両方で読めるように。

| 画面 | 見る人 | 主な内容 |
|---|---|---|
| トップ | GM | GM合言葉 → 設定（共通／個別、シナリオ／聞き込み、目的の選択肢あり／なし、GMも参加、グループ数）→「部屋を作る」。既存の部屋にGMとして入り直す欄 |
| GM画面 | GM | 部屋URLとQRコード、いまのフェーズと「次へ」「1つ戻る」、台本（v1の SCRIPT）、チームの一覧（G1-A：メンバー名、カード、確定の有無）、出来事の記録、設定（lobby・reviewのとき） |
| 参加 | 参加者 | ニックネーム入力 |
| チーム選択 | 参加者 | グループとA／Bを選ぶ。各チームの人数を表示 |
| カード提示〜振り返り | 参加者 | 4.2の表のとおり。上部にフェーズの並び（いまの位置）、自分のチームとメンバー名、接続状態 |
- 「時間は Balus のタイマーで確認してください」の表示は v1 と同じ。
- QRコードは画面側で作る（npmのライブラリを同梱。外部CDNに頼らない）。

## 9. 保存
- 部屋はメモリに持ち、変化があれば1秒以内にまとめて `/var/lib/modetective/rooms.json` へ書く（一時ファイルに書いてから置き換え）。起動時に読み戻す。
- 最後の操作から48時間で部屋を消す（K8）。部屋数の上限は50。
- 保存は差し替え口（インタフェース）を通す（ITBと同じ考え方。将来Cloud Runに移すときに差し替える）。

## 11. デプロイ
- 画面：`pnpm --filter web build` → WING の `public_html/modetective.m-miura.jp/` へ rsync（SSHポート8022）。index.html はキャッシュしない、ハッシュ付きファイルは長期キャッシュ（.htaccess）。
- サーバー：ビルド → tar → `gcloud compute scp --tunnel-through-iap` → VMで `/opt/modetective/releases/<日時>/` に展開 → `/opt/modetective/current` を切り替え → `systemctl restart modetective`。再起動しても部屋は戻る。
- 最初は手元のスクリプト（Windowsのコマンドプロンプトで動く形）、慣れたら GitHub Actions。
